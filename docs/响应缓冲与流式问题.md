# 响应缓冲（Buffering）与流式响应的问题记录

> 起因：为了把 `ServeMux` 默认的纯文本 `404/405` 改写成统一 JSON 信封，我们写了一个
> `httpx.JSONErrors` 拦截器。它带来一个**副作用**——响应会被「全量缓冲」后再一次性发送。
> 本文记录这个副作用的来龙去脉、影响边界，以及将来加流式/下载接口时必须遵守的规则。

## 1. 现象：响应「等 handler 写完才一次性发出」

正常情况下，服务端 `w.Write(...)` 写多少，客户端就该很快收到多少（边写边推）。
但被 `JSONErrors` 包过之后，**所有响应都要等到 handler 完全执行结束**，才一次性发给客户端。

对**小 JSON 接口**（本项目现有全部接口）——毫无影响，因为数据本来就是一瞬间就绪的。
问题只在两类接口才暴露：**流式（SSE）** 和 **大文件下载**。

## 2. 根因：`captureWriter` 把响应「扣下不发」

代码位置：[`internal/httpx/response.go`](../internal/httpx/response.go) 的 `JSONErrors` + `captureWriter`。

```go
buf := &captureWriter{header: make(http.Header)}
next.ServeHTTP(buf, r)      // handler 的输出先进 buf，不直接发给客户端
// ...等 handler 跑完，判断是不是 mux 默认错误页，再决定怎么写给真正的 w
```

`captureWriter.Write` 把数据写进内部 `bytes.Buffer`，**没有转发给真正的 ResponseWriter**。
为什么要这样？因为必须**先拿到最终状态码**，才能判断「这是不是 404/405、要不要改写成信封」。
这个「先看到、再决策」的需求，决定了它只能全量扣住。

## 3. 三层「缓冲」辨析（别混为一谈）

| 层 | 出处 | 目的 | 会不会扣住响应 |
|---|---|---|---|
| ① net/http 内置小缓冲 | 标准库，约 2~4KB | 减少系统调用 | 几乎无感，超过阈值自动 flush |
| ② 旁路抄送型 | jyddms `middleware/operation.go` 的 `responseBodyWriter` | 复制一份记日志 | **不会**：`Write` 里 `return 真正的writer.Write(b)`，直传 |
| ③ 我们的全量缓冲 | `httpx.captureWriter` | 先看状态码再决定是否改写 | **会**：handler 跑完前不发 |

关键对照——jyddms 的写法天生没有这个副作用：

```go
// jyddms/server/middleware/operation.go
func (r responseBodyWriter) Write(b []byte) (int, error) {
	r.body.Write(b)                      // 抄一份用于记日志
	return r.ResponseWriter.Write(b)     // 同时立刻透传给客户端（直传）
}
```

它「照发不误、顺带复印」；我们「扣下不发、等决策」。差别就在这一行转发。

## 4. 什么时候会成为真正的坑

- **SSE / 服务器推送 / 边算边流式返回**：
  这类代码会 `w.Write(chunk); flusher.Flush()` 期望每片即时送达。
  但 `captureWriter` 把 `Flush` 架空了（它没有真正的下游可 flush），客户端只能等全部算完才收到 → 「实时」失效。
- **大文件下载**：
  整个文件被先读进内存 `bytes.Buffer` 再发送 → 几百 MB 直接内存爆掉，且首字节延迟极高。

## 5. 规则（将来加这类接口时必须遵守）

> **凡是流式(SSE)或大文件下载的路由，绝不能被 `httpx.JSONErrors` 包裹。**

两种实现方式任选其一：

1. **路由分流**：把流式/下载接口注册到一个**不套 `JSONErrors` 的 mux** 上，普通 JSON 接口才走 `JSONErrors(mux)`。
2. **改写成直传**：把 `captureWriter` 从「全量扣住」改成 jyddms 那种 **write-through（边发边抄）**，只有确判为默认错误页时才改写。代价是无法再改写已经发出去的字节——需要更早（写 header 前）就决定，实现更复杂。

现阶段项目**没有任何流式/下载接口**，所以本副作用**暂无实际影响**；此文档用于**提前埋点提醒**，避免将来加这类接口时踩坑。

## 6. 快速自检

新增接口时，如果它属于以下任一情况，请**绕开 `JSONErrors`**：
- 返回 `text/event-stream`（SSE）
- 主动调用 `http.Flusher` 的 `Flush()`
- 用 `io.Copy(w, bigReader)` 发送大 body
- 用 `http.ServeContent` / `ServeFile` 发文件
